#### HTTP 的特点

**无状态**；支持不同数据格式（HTML、XML...）；**请求应答模式**

#### HTTP 报文结构是什么？

请求报文：

+ **请求行**：包含**请求方法**、**请求目标**（URL或URI）和HTTP协议版本。
+ **请求头部**：包含关于请求的**附加信息**，如 **Host**、User-Agent、**Content-Type**（text、Json）、**keep-alive** 等。
+ 空行：请求头部和请求体之间用空行分隔。
+ **请求体**：可选，包含请求的数据，通常用于POST请求等需要传输数据的情况。

响应报文：

+ **状态行**：包含HTTP协议版本、**状态码**和状态信息。
+ **响应头部**：包含关于响应的附加信息，如 **Content-Type**、Content-**Length**、**keep-alive** 等。
+ 空行：响应头部和响应体之间用空行分隔。
+ **响应体**：包含响应的数据，通常是服务器返回的HTML、JSON等内容。

*（通过状态码去记状态行）*

#### HTTP 协议的请求头有什么？

常见的有：

+ User-Agent：告诉服务器你是谁，服务器用来做兼容性处理，下面是一些例子。

  ```
  // Chrome浏览器
  Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/126.0.0.0 Safari/537.36
  // Android App (OkHttp)
  okhttp/4.12.0
  ```

+ Content-Type：告诉服务器，发送的请求体（Body）是什么格式。下文有专门介绍。

+ Accept：告诉服务器，希望返回什么格式。

+ Authorization：Token 令牌。

+ Cookie：携带客户端的 Cookie 信息。

+ Connection：控制连接是否保持，常见值有 keep-alive（保持连接，后续请求可以复用这条 TCP 连接；一般会配合 timeout 和 max 参数，避免长时间占用服务器资源）。

+ Cache-Control：缓存策略，如 no-cache 表示不直接使用缓存，需向服务器验证；no-store 表示不使用缓存。这些策略由浏览器/HTTP 客户端自动执行。

#### HTTP 请求类型了解哪些？

+ GET：用于请求**获取**指定资源，通常用于获取数据。

+ POST：用于向服务器**提交**数据，通常用于提交表单数据或进行资源的创建。

+ PUT：用于向服务器**更新**指定资源，通常用于更新已存在的资源。
+ DELETE：用于请求服务器**删除**指定资源。
+ HEAD：类似于GET请求，但**只返回资源的头部信息**，用于获取资源的元数据而不获取实际内容。

HTTP 请求方法是为了服务器功能实现起来更方便，但不意味着每种特定的方法只能实现某种特定的功能，最重要的还是开发者如何开发设计。

#### Get 和 Post 的区别？

+ Get 提交的数据会放在 URL 之后，Post 提交的数据放在 body 上。
+ Get 会存在安全问题，而 Post 数据放在请求主体中，且数据不会被浏览器记录。
+ Post 可以进行**复杂的加密**，Get 则不可以。
+ Get 提交的**数据大小有限制**，而 Post 方法提交的数据理论上没限制。
+ 从语义来看，Get 方法具有幂等性（因为它是只读操作，实际过程中取决于开发者），Post 方法不具有。

#### HTTP 状态码了解哪些？

+ 1xx：**提示信息**，表示目前是协议处理的中间状态，还需后续操作，**用的少**。

+ 2xx：**成功**，报文已经收到并被正确处理。

+ 3xx：**重定向**，表示自愿位置发生变动，需要客户端重新发送请求。（`return "redirect:https://new.example.com";` 客户端会请求重新请求这个链接）

+ 4xx：**客户端错误**，请求的报文有错误，服务器无法处理。

+ 5xx：**服务器错误**，服务器在处理请求时内部发生了错误。

常用状态码：

+ 200：请求成功。

+ 301：永久重定向（浏览器会记住）；302：临时重定向。

+ 404：请求页面不存在；405：请求的方法类型不支持；403：禁止访问（权限）

+ 500：服务器内部出错；502：网关错误（比如假设 Nginx 是代理服务器，收到客户端的请求后，将请求转发到后端服务器，当 Nginx 收到了无效的响应时，就返回 502）；504 网关超时（当 Nginx 超过自己配置的超时时间，还没有收到请求时，就返回 504 错误）；503：服务不可用。

301例子，比如你请求一个 http 开头的网站，然后会（浏览器）重定向到一个 https 的网站。

```nginx
server {
  	listen 80;
  	server_name example.com;
  	return 301 https:
}
```

*（记忆：没有503，所以403是禁止访问）*

#### HTTP 的长连接是什么？

HTTP 协议采用的是“**请求-应答**”的模式，也就是客户端发起了请求，服务端才会返回响应，一来一回这样子。由于 **HTTP** 是基于 TCP 传输协议实现的，所以流程变成了“**建立 TCP -> 请求资源 -> 响应资源 -> 释放连接**”，这就是短连接。

![image-20241219115539296](/Users/mato/Library/Application Support/typora-user-images/image-20241219115539296.png)

像这样进行一次 HTTP 通信就要新建一个 TCP 连接，对于客户端和服务器的压力是很大的。能不能在第一个 HTTP 请求完后，先不断开 TCP 连接，让后续的 HTTP 请求继续使用此连接？这就是长连接，HTTP 的 **Keep-Alive**（字段） 可以实现这个功能，**能够让同一个 TCP 连接来发送和接收多个 HTTP 的请求和应答，避免了连接建立和释放的开销**。

<img src="/Users/mato/Library/Application Support/typora-user-images/image-20241219115602365.png" alt="image-20241219115602365" style="zoom:33%;" />

**什么时候会中断？**

+ 当服务端或者客户端执行 **close** 系统调用的时候，会发送 **FIN** 报文，就会进行四次挥手的过程。
+ 当发送方**发送了数据**之后，接收方超过一段时间**没有响应 ACK 报文**，发送方重传数据达到最大次数的时候，就会断开TCP连接。
+ 当 HTTP **长时间没有收到请求和响应**的时候，超过一定的时间，就会释放连接。

#### HTTP 和 HTTPS 的区别？

+ HTTP 是超文本传输协议，信息是**明文传输**，存在安全风险的问题。HTTPS 在 **HTTP（应用层） 和 TCP（传输层）**层之间加入了 SSL/TLS **安全协议**，使得报文能够**加密传输**。
+ HTTP 连接建立相对简单，TCP 三次握手之后便可进行 HTTP 的报文传输。而 HTTPS **在 TCP 三次握手之后，还需进行 SSL/TLS 的握手**过程，才可进入加密报文传输。
+ 两者的默认端口不一样，HTTP 默认端口号是 **80**，HTTPS 默认端口号是 **443**（http://192.168.1.100 就是访问 http://192.168.1.100:80，大部分服务都是要自定义端口的）。
+ HTTPS 协议需要**向 CA（证书权威机构）申请数字证书**，来保证服务器的身份是可信的。

#### HTTP 是不保存状态的协议，如何保存用户状态？

HTTP 是无状态的，这意味着每个请求都是独立的，不会对请求和响应之间的通信状态进行保存。也就是说 HTTP 协议对于发送过的请求和接受过的请求都不做持久化处理，这样可以**更快地处理**大量事物。

虽然 HTTP 本身是无状态的，但可以通过一些机制来实现状态保持，其中最常见的方式是使用 **Cookie 和 Session** 来跟踪用户状态。

**Cookie**

Cookie **实际上是一小段的文本信息**。客户端请求服务器，如果服务器需要记录该用户状态，就使用 response 向客户端浏览器颁发一个Cookie。客户端浏览器会把 Cookie 保存起来。当浏览器再请求该网站时，浏览器把请求的网址连同该 Cookie 一同提交给服务器。服务器检查该 Cookie，以此来辨认用户状态。服务器还可以根据需要修改 Cookie 的内容。

Cookie 是**不可跨域名**的，很多网站都会使用 Cookie。例如，Google 会向客户端颁发 Cookie，Baidu 也会向客户端颁发 Cookie。那浏览器访问 Google 会不会也携带上 Baidu 颁发的 Cookie 呢？答案是不会的。**不同域名的 Cookie 不会互相影响**。**Cookie 在客户端是由浏览器来管理的**。浏览器能够保证 Google 只会操作 Google 的 Cookie 而不会操作 Baidu 的 Cookie，从而保证用户的隐私安全。

Cookie 主要用于以下三个方面：

- 会话状态管理（如用户登录状态、购物车、游戏分数或其它需要记录的信息）
- **个性化设置**（如用户自定义设置、主题等）
- 浏览器行为跟踪（如跟踪分析用户行为等）

Cookie 的缺陷：

+ **保存在客户端，容易被盗取或者利用**
+ 单个 Cookie **只能存储 4kb** 的数据
+ **不可跨域**

**Session**

Session 是另一种记录客户状态的机制，不同的是 Cookie 保存在客户端浏览器中，而 Session **保存在服务器上**。**客户端浏览器访问服务器的时候，服务器把客户端信息保存在服务器上**。客户端浏览器再次访问时只需要从该 Session 中查找该客户的状态就可以了。

**Session 是基于 Cookie 的**。第 1 次请求时，服务器会把一个 **sessionid** 以 cookie 形式传给浏览器。以后客户端在访问服务端时候，HTTP 请求会带着 sessionid，服务器会先检查这个客户端的请求里是否已包含了一个 sessionid。如果已包含这个sessionid，则说明以前已经为此客户端创建过session，服务器就根据这个sessionid 把相对应的 session 检索出来使用。

```java
StandardSession session = (StandardSession) manager.findSession(sessionId);
return session;
```

为啥要 sessionid？**维持会话**，登陆后给一个 sessionid，经过设定的天数后销毁这个 sessionid。得重新登陆。只用 cookie 没法维持会话。

Session 的缺陷：

+ Session 是存储在服务器端，巨大并发的时候会使**服务器资源急速飙升**。（为啥不都放到 Cookie 里？安全性；存储大小限制；Cookie 的过期时间由客户端管理，服务器端无法控制）
+ 如果后端机器是多台的话，因此**多个机器间是无法共享 Session** 的。

**禁用了 Cookie，Session 还能用吗？**

不能；替代方式每次请求时，手动把 sessionid 带上，来识别用户。

**Token**

相比于 Session，登陆后，服务器返回的 Cookie 带着的是 token。之后每次请求时会带上这个 token，服务端直接验证，**服务器可以独立地对令牌进行验证**，而不需要依赖其他服务器或共享存储。这使得集群中的每个服务器都可以独立处理请求，提高了系统的可伸缩性和容错性。相比于 Session，不在需要在服务端存储 sessionID。这个过程也叫 JWT（Json Web Token）。

而解析出的令牌，包含所有必要的**身份**验证（用户身份、权限、令牌有效期）和**会话信息**（相关属性，如偏好设置），使得服务器无需存储会话信息，从而解决了集群部署中的身份验证和会话管理问题。

在传统的基于会话和 Cookie 的身份验证方式中，会话信息通常存储在服务器的内存中。但在集群部署中，不同服务器之间没有共享的会话信息，这会导致用户在**不同服务器之间切换时需要重新登录**，或者**需要引入额外的共享机制**（如Redis），增加了复杂性和性能开销。

JWT 的缺点：

JWT 一旦派发出去，**在失效之前都是有效的**。所以如果令牌泄露了，可以增加黑名单机制。使用内存数据库比如 Redis 维护一个黑名单，如果想让某个 JWT 失效的话就直接将这个 JWT 加入到黑名单即可。然后，每次使用 JWT 进行请求的话都会先判断这个 JWT 是否存在于黑名单中。

#### HTTP、SOCKET 和 TCP 的区别

**Socket 提供了网络通信的底层通道**，**是应用层与传输层间的一个抽象接口**，它负责在客户端和服务器之间建立连接并传输数据。Socket 地址通常是协议类型、IP 地址和端口号的组合。

**HTTP 是一个基于 Socket 的应用层协议**，**它使用底层的 TCP Socket 来发送和接收 HTTP 请求和响应**。

（HTTP（超文本传输协议）是用于在客户端（如浏览器）和服务器之间传输网页数据（如HTML、图片）的协议）


#### HTTP 不同版本的区别？

1. HTTP 1.0：最早的 HTTP 版本，采用**短连接方式**，每次请求都需要建立和关闭 TCP 连接。它的主要特点是简单，但存在以下问题：
   - 每个请求都需要建立新的 TCP 连接，造成了**较大的开销**。
   - 不能复用连接，无法进行流水线处理，导致效率低下。
2. HTTP 1.1：在 HTTP 1.0 的基础上进行了一些改进，引入了长连接（Keep-Alive）和流水线技术，以提高性能。主要改进包括：
   - 引入了**长连接**，允许多个请求和响应复用同一个TCP连接，减少了连接建立和关闭的开销。
   - 引入了**流水线处理**，**可以同时发送多个请求，无需等待前一个请求的响应**。（可以想想代码中，发了一个请求还没收到结果，又发；虽然可以在单一连接中发送多个请求，**但请求和响应是顺序的**）
3. HTTP 2.0：HTTP 2.0 将数据传输方式从文本格式改为二进制格式，并引入了多路复用技术。主要改进包括：
   - 使用**二进制帧**替代了 HTTP 1.x 的**文本格式**，减少了数据量和解析开销。（虽然最终都是二进制传输，但 2.0 报文就是用的二进制）
   - 引入了**多路复用**技术，可以在一个 TCP 连接上同时发送多个请求和响应，提高了并发性能。（和 I/O 多路复用两码事；**在一个长连接中并发多个请求和响应**）
   - 支持服务器**主动推送**（Server Push），客户端发送一个请求（如请求 HTML 文件），服务器在返回 HTML 文件的同时，主动推送 HTML 中引用的其他资源（如 CSS、JavaScript）。
4. HTTP 3.0：HTTP 3.0 基于 UDP 协议，并使用 QUIC（Quick UDP Internet Connections）传输协议。主要改进包括：
   - 使用 **UDP** 协议替代了 TCP 协议，低延迟。
   - 使用 **QUIC** 协议，进一步提升了网络连接的速度和**可靠**性。
   - 使用 TLS 1.3 作为底层安全协议。

###### 最终传输都要变成二进制，HTTP 2.0 的二进制为什么更节省空间？

HTTP 2.0直接在开始处就使用了相应的方式，用二进制表示去节省空间，1.0 是最后传输时才变成二进制。

```
GET /index.html HTTP/1.1\r\n
Host: www.example.com\r\n
User-Agent: Mozilla/5.0\r\n
Accept: text/html\r\n
Connection: keep-alive\r\n

+-----------------------------------------------+
| 长度 | 类型 | 标志 | 流 ID | 数据内容          |
+-----------------------------------------------+
| 0x00 | 0x01 | 0x04 | 0x0001 | 压缩头部数据   |
+-----------------------------------------------+
```

###### 流水线处理和多路复用差别？

+ 流水线处理：按顺序发送多个请求，按顺序接收响应。它只是说可以一起发多个，但**前一个请求未完成，也会阻塞后续请求**。
+ 多路复用：同一连接（一个 TCP 连接）中**并发**发送多个请求与接收响应，**请求和响应无序**，按流 ID 区分数据流。

#### CDN 干什么用的

**内容分发网络**（Content distribution network）是一种分布式服务器网络，它**将内容缓存到全球多个数据中心**（边缘服务器），用户从最近的服务器获取资源，从而提高访问速度和可靠性。

CDN 的流程：

1. 用户请求内容： 用户通过浏览器请求网站资源（如图片、视频、网页等）。
2. DNS 解析： 用户的请求首先通过 DNS 服务器解析到最近的 CDN 边缘服务器。
3. 内容分发：
   - 缓存命中（Cache Hit）：如果边缘服务器已有请求的内容，直接返回给用户。
   - 缓存未命中（Cache Miss）：如果边缘服务器没有内容，则从源站（主服务器）拉取资源，并缓存到边缘服务器。
4. 返回响应：用户从最近的 CDN 边缘服务器接收内容（当未命中时，边缘服务器（CDN 服务器）会从主服务器拉取内容，并将其存储到 CDN 缓存中，然后再将该内容返回给用户）。

主要好处：

+ **提高访问速度**。
+ 提升网站稳定性和可用性：可以做负载均衡、自动故障切换
+ **减少服务器负载与带宽成本**（请求不需要都走主服务器）：

+ 增强安全性：流量清洗抵御DDoS 攻击，HTTPS 加密支持

####  HTTP请求体常见格（POST 请求有几种形式）

HTTP 请求体（Request Body）的格式主要通过 HTTP 请求头中的 Content-Type 字段来声明。服务器根据这个字段来解析接收到的数据。以下是开发中最常见的几种 HTTP 请求体格式：

1）JSON 格式（`application/json`）

这是目前 Web API 中最常用的格式，数据以 JSON 字符串的形式发送，支持复杂的嵌套结构。

```http
POST /api/user HTTP/1.1
Content-Type: application/json

{
  "name": "张三",
  "age": 25,
  "skills": ["Java", "Python"]
}
```

2）表单格式（`application/x-www-form-urlencoded`）

这是传统 HTML `<form>` 表单在没有文件上传时的默认格式。数据会被编码为键值对，并用 & 连接，特殊字符会被转义。这种格式是无法直接上传文件，虽然可以通过 Base64 等手段将二进制数据编码为文本，但会导致请求体体积膨胀很多，传输效率极低。如需上传文件，需 `multipart/form-data`。

另外这个和 Query 的差别是，这个是放在 Body 里的，Query 是放在 URL 后面的（POST 请求也能带 query，但 GET 是不能带请求体的）。

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=zhangsan&password=123456&remember_me=true
```

3）多部分表单格式（`multipart/form-data`）

这种格式主要用于上传文件，或者同时发送文件和文本字段。它会使用一个随机生成的 boundary（边界字符串）来分隔不同的字段。

`multipart/form-data` 传文件的方式和 `application/x-www-form-urlencoded` 有什么区别呢？`multipart/form-data`  文件直接以原始二进制字节传输，而  `application/x-www-form-urlencoded` 需经过文本编码，因为它本质是是进行 URL 编码，这就会涉及到需要对像 “&”、“=”、“?”、空格等字符进行特殊编码，降低传输效率。

```http
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="username"

zhangsan
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="avatar"; filename="photo.jpg"
Content-Type: image/jpeg

(这里是图片的二进制数据)
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

4）纯文本格式（`text/plain`）

数据以纯字符串的形式发送，不做任何特殊的格式化处理。

```http
POST /log HTTP/1.1
Content-Type: text/plain

这是一条普通的日志信息。
```

5）XML 格式（`application/xml` 或 `text/xml`）

在 JSON 流行之前，XML 是主要的数据交换格式。现在多见于一些老旧系统或特定的行业标准。

```http
POST /api/save HTTP/1.1
Content-Type: application/xml

<user>
    <name>张三</name>
    <age>25</age>
</user>
```

6）二进制流（`application/octet-stream`）

用于传输未知的二进制数据。通常在只上传一个文件（且不需要其他表单字段）时使用，比如上传一个图片、压缩包或 PDF。

```http
POST /download/file HTTP/1.1
Content-Type: application/octet-stream

(二进制数据...)
```

7）总结

| 格式           | Content-Type                      | 主要用途                            | 特点                                       |
| -------------- | --------------------------------- | ----------------------------------- | ------------------------------------------ |
| **JSON**       | application/json                  | 现代 API 交互、移动端/Web 开发      | 结构化强、轻量、主流、易读                 |
| **表单**       | application/x-www-form-urlencoded | 基础表单提交（登录、简单搜索）      | 兼容性高、处理简单、无需特殊解析库         |
| **多部分表单** | multipart/form-data               | **文件上传**、混合传输（文件+字段） | 支持二进制传输、适合上传大文件             |
| **纯文本**     | text/plain                        | 简单的日志、指令传输、监控数据      | 极简、无需额外解析格式，但不适合结构化数据 |
| **XML**        | application/xml                   | 旧系统、特定行业接口（如支付）      | 结构严谨但冗余，解析相对耗资源             |
| **二进制流**   | application/octet-stream          | 单个原始文件传输（图片、压缩包）    | 效率高，无任何封装开销，直接发送字节流     |

另外，Content-Type 重要吗？我之前的理解是，这个主要取决于后端怎么去解析，完全可以不管前端传的是什么 Content-Type，全当作 JSON 处理。理论上是的， 但现在的后端开发大多是基于框架的，框架会根据你发送的 Content-Type 自动分发给不同的处理逻辑。比如在 Spring Boot 中，`@RequestBody` 只从请求体中按 JSON 解析；`@RequestParam` 则从 URL 查询参数或表单格式的请求体中查找。不仅如此呢，防火墙、网关可能也会校验你穿的内容和  Content-Type 是不是相符的。所以还是应该按照既定的规则去进行传输。
